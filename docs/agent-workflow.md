# 协作规则（智能体工作约定）

> 这份是**给智能体看的工作约定**，不是给玩家的功能文档。
> 本仓库按「一个仓库维护多个角色 mod」的方式组织：每个角色 mod 各自一份设计表与代码，
> 下面的规则对**所有角色 mod** 通用。文中出现的具体名称、路径、数值都只作**示例**，
> 换成当前正在维护的角色 mod 即可。
>
> 目录约定（通用）：
>
> - 角色 mod 工程：`<角色名>/mods-src/<角色名>/`（内含 `src/`、`design/`、`assets/`）
> - 仓库级资源：`resources/...`（美术源文件、派生图等）
> - 构建产物：`dist/<角色名>/...`
> - 所有工具集中在工作区根的 `tools/`，用 `-c/--character`（Python）或 `-Character`（PowerShell）指定角色，例如 `python tools/cardspec.py -c saria`。

## 1. 触发式工作，不做例行巡检

除非用户说「检查文档更新 / 更新新内容 / 看看有什么要做的」这类指令，**默认不要**主动跑
`cardspec.py --pending` 并开始实现待办。

用户只发一条具体指令（例如「改一下某张卡」「写个文档」「启动游戏」）时：
- 只做那件事；
- 不顺手把攒着的待实装内容做掉。

理由：单批内容扩展太碎，用户希望自己控制节奏。

## 2. 只处理「被标记」的内容

需要智能体实现/修改/删除的依据，**只看设计表里的状态标记**：

| 标记 | 智能体的动作 |
|---|---|
| `待实装` | 实现 |
| `待修改` | 按备注改 |
| `待删除` | 删代码 + 删表里这一条 |
| `已实装` | **不看** |

设计表是**唯一事实来源**：先改表、再改代码、再跑 `cardspec` 校验、最后用 `tag_implemented`
把标记推进到 `已实装`。

## 3. 已实装条目的「数值差异」不归智能体管

用户在反复调整数值时会直接改设计表（或自己改代码）。因此：

- 标记为 `已实装` 的卡牌，**表里的数值和代码不一致时，不要改、不要提示**；
- 也不要因为数值不同去重新实现或对齐；
- 文案（措辞）不一致仍然值得提示，数值不一致不算问题。

工具侧注意：`check_text_matches` 已经把数字剔除后再比对，所以数值不同不会误报——保持这个设计。

## 4. 有需要才跑校验

`cardspec.py` 的默认全量校验只在以下情况跑：
- 刚改过代码/设计表（改完自检）；
- 用户要求检查；
- 怀疑状态标记或结构有问题。

平时不必每轮跑一遍然后罗列一堆「建议」。

## 5. 每轮收尾仍然要做的（属于交付质量，不是巡检）

- 改完代码后：编译；能部署就部署（把 dll 拷到 `mods/<角色名>/`；游戏开着则说明需要重启）；
- 用户没要求启动游戏时**不要启动**；
- 改动提交 git。

## 6. 不要读的文件

- 用户的私人笔记文件（例如 `docs/user-temp.md`）——绝大多数情况下**不用看**。
  只有用户明确说「看一下 user-temp」时才读。

## 7. 用户偏好速记

- 游戏内文本用用户写的原文，不改写、不加修饰；`<br>` = 换行，`{Amount}` / `{N*Amount}` 是变量写法。
- 描述结尾要有句号、中文里不留空格（`normalize_text.py` 自动处理）。
- 数值调整用户自己也能做，参见 `docs/card-spec-format.md` 和 `tools/apply.ps1 -Character <角色名>`。
- 不要擅自扩大改动范围；有歧义先问。

## 8. 反复纠错太久 → 主动停下来汇报

单轮对话里出现下面这些情况，**不要一路硬顶**：

- 同一处问题连续改 3 次以上还没解决；
- 实机测试反复报错，需要不停重启游戏、换场景验证；
- 为了验证一个行为得搭一堆临时脚手架（改常量、改数据、造测试局）。

这时应该**中断当前任务进度**，改成汇报：

1. 现在卡在哪一步、具体现象（附日志/截图/实测数据）；
2. 已经排除或验证过什么（例如「hook 未被派发」「该路径不经过格挡」）；
3. 判断的可能原因与候选方案。

然后等用户指示。用户往往知道一条更短的验证路径（例如指定用哪个敌人、哪张卡去测），
硬试下去只是浪费时间。

> 注意区分：**正常的实现难度**不要停（该查源码就查、该编译就编译）；
> 这里说的是**反复试错没有进展**的情况。

## 9. 用户说「有问题就问」时 → 先列清单，全部解决再动手

只要指令里出现「有问题就问 / 有疑问直接问 / 不确定的问我」这类话，
就把当轮**所有**没有十足把握的点一次性列出来，而不是边做边猜、也不是只挑一两个问。

每条写清三件事：

1. 描述原文（或位置）——引用用户写的那句话；
2. 智能体读到的意思——理解；
3. 具体不确定在哪——给出二选一／多选，或说明「这两种结果差在哪里」。

规则：

- **先问完，再实装**：任何一条没答复之前，不要开始写代码／改数据，避免做一半再返工；
- 一次性提多个问题（可以一次问 3~5 条），别挤牙膏；
- 实现过程中如果又冒出新的歧义，**立刻停下再问**，不要自己替用户决定；
- 用户跳过或说「随便」的条目，按最保守的理解实现，并在汇报里单独说明「这条我按 X 处理」；
- 汇报时先给问题清单，等用户答完再给「已实装」的结论。

## 10. 日常只做本地 git，推送等用户点名

- 后续的增量与修改**只做本地 git 提交**，不要自动 `git push`；
- 需要同步到线上（GitHub）时，**用户会显式提醒**（例如「推送」「推一下」「上传」）；
- 顺带：**不要主动打 Release、不要主动改版本号**，这些也只在用户要求发版时做（流程见 `docs/release.md`）。

换言之：提交是日常收尾的一部分，推送/发版是单独的、由用户发起的动作。

## 11. 不主动启动游戏测试

**非必要的实机测试由用户来做**，后续都这样。

- 改完代码只做：编译 → 部署（把 dll 拷到 `mods/<角色名>/`）→ 本地 git 提交 → 汇报；
- **不主动启动游戏**做验证，也不为验证去搭临时测试局；
- 需要实机确认时，把「要测什么、看什么现象」写清楚交给用户；
- 若确实必须由智能体这边跑（例如只有运行时才能拿到的数据），先问一句再做。

## 12. 网络操作走工作区代理

工作区里有代理配置文件（如 `.dsh/proxy.json`，由用户维护，**故意入库**）：

```json
{
  "env": {
    "HTTP_PROXY": "http://127.0.0.1:6696",
    "HTTPS_PROXY": "http://127.0.0.1:6696"
  }
}
```

需要联网时（git fetch/push、GitHub API、web_fetch 等），先把这两项环境变量设上再执行
（具体端口以该文件为准）；推送流程见 `docs/release.md`，令牌用一次就撤销。

## 13. 卡牌与状态不一致时必须上报

更新过程中如果发现**卡牌描述/效果与对应的 power 行为不一致**，
必须**明确上报**，不允许静默按自己的理解改掉。

- 发现不一致 → 在汇报里单列一段：哪张卡、哪条描述、power 实际怎么做、差在哪；
- 按设计表改代码可以照做，但要在汇报里点名「这条原来是 X，代码做的是 Y」；
- 若设计表本身没写清，先问再做。

**同样适用于「设计表缺条目、而卡牌需要它才能跑」的情况**：
哪怕问题看起来「根本不用讨论」，也要**先上报再做**，不要自行补齐后当成正常实现。

> 示例：某张卡的效果需要一个对应的 power，但设计表当时没有这条 power ——
> 如果悄悄把 power 写进代码，结果就是 `design/power-ids.md`（power 清单）里缺条目、用户后补的表格与代码状态对不上。
> 提问和上报从来不是问题，不要因为觉得麻烦而省略。

## 14. 创意工坊：未经专门指令不得上传

**没有专门的「上传创意工坊」指令时，一律不得执行上传或修改线上条目**。

- 禁止：`ModUploader.exe upload`、改 `visibility`、删条目、改线上标题/描述/预览图；
- 允许（本地）：改 `steam/` 里的文案、跑 `tools/sync_workshop.py -c <角色名>` 更新本地 `workshop.json`、准备封面与预览图；
- 发版节奏：用户会自己决定何时把仓库版本升到正式版并通知，届时才同步工坊并转 public；
- 每个角色 mod 各有自己的工坊条目，条目 ID 记录在 `dist/workshop/<角色名>/mod_id.txt`；
  首次发布前保持 `private`（示例：条目 ID 形如一串数字，以该文件为准，不要写进文档正文）；
- 默认语言槽放**简体中文**（`steam/zh_cn/`），英文等其他语言由用户在网页端补。
